# 开发工作流（效率约定）

## 为什么需要这份文件

这个项目没有本地 Android SDK、没有真机、没有模拟器，历史上出现过三类反复：
1. 界面预览与成品水印不一致 → 返工两次（两套绘制代码的锅）
2. 样式类需求靠"改完装机看效果"验证 → 每轮 10 分钟以上，且用户要反复描述不满意在哪
3. 需求以对话碎片形式进来 → 每轮重新理解，容易漏项

下面是把这三类堵住的固定做法。

## 一、交付流水线（唯一路径）

```
改代码
  → git push origin main        # 触发 CI：单测 + Debug + Release 编译
  → 确认 CI 双绿               # 红的话看 gh run view --log-failed 里的 "e: file"
  → git tag -a vX.Y.Z && push  # 打 tag 才会用正式 keystore 签名
  → gh run download <run id> -n SiteStamp-Release-APK
  → 交付 APK（签名一致，用户可直接覆盖安装）
```

- **不要**给用户 debug 包（签名每次不同，覆盖安装会失败）
- **不要**在 CI 红的情况下打 tag
- 一轮 CI 约 3–5 分钟，所以一次 push 要尽量把同类改动凑齐，但别混多类风险

## 二、样式类改动：先离线出样张

水印外观、界面布局这类"看着才知道好坏"的改动，**先用 PIL 按同一套比例参数复刻出图**，
给用户看图确认，再落 Kotlin。

原因：渲染参数都是以照片宽高/卡宽归一化的浮点数，PIL 复刻与 Kotlin 实现能做到参数级同构；
一张样张能让用户直接说"这里太挤/这里颜色不对"，比改完装机再回炉快一个数量级。

复刻脚本放在 `cache/scratch/` 下的项目专用脚本里，改完存档，下次直接改参数重跑。

## 三、需求落地：先改 SPEC 再改代码

对话里的碎片要求，先落到 `docs/SPEC.md` 对应小节（哪怕只加一行），再动手。
好处：跨会话不丢上下文；下一轮接手的人（或 agent）知道当前口径是什么。

## 四、一轮只改一类事

- 布局 / 水印 / 逻辑 / 配色，分开提交
- 混在一起时 CI 一旦红，无法判断是哪类引入的
- 若必须同时改，先本地 grep 检查共享函数的调用点（`drawLogoBadge` 就因此被误删过两次）

## 五、交付话术

- 只说三件事：改了什么（对应哪条诉求）、怎么验证的、还有什么没验证
- 不说"已完美优化"这类空话；没装机验证的部分必须写明
- 出问题先说现象与定位，不解释"为什么会这样"的长篇分析

## 六、待补齐（下一步）

- [ ] CI 里用 Robolectric 渲染水印样张，作为 artifact 上传 → 改样式时不必再靠 PIL 猜
- [ ] 界面截图回归：同一屏幕改动前后对比图，随 PR 输出
- [ ] 把"水印参数"抽成一份 JSON（真机与离线样张共用），彻底消除两套参数的可能
